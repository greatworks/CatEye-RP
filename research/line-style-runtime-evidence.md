## 1. Pattern and width state updates

`style.js:1219–1221`: `linePattern == 'none'` emits `.stroke { stroke-width:0; stroke-dasharray:0 }`. It sets the **arrowhead rule's fill to none only**, skipping the subsequent width/dash calculation. It does not explicitly zero an arrowhead's own stroke or rewrite its geometry. Therefore this source rule alone must not be summarized as proof that every possible preexisting arrowhead pixel disappears.

Otherwise, `1223` gates the following work on a truthy `borderWidth`. `1356–1359` emits each `linePatternArray` entry multiplied by that requested width, joined by commas. The `linePattern` label alone does not synthesize a dash sequence. A probe with width2.5 and `[3,1,.5,1]` produces `7.5,2.5,1.25,2.5`. Odd arrays and zero entries are retained; an empty array emits an empty declaration. Width0 or absent width skips this branch and does not reset an existing path width attribute. These are direct function results, not recommendations to expose unrestricted custom arrays.

`1026–1034` replaces the generated state stylesheet on each application. Missing declarations therefore fall back to the initial SVG attributes/CSS; they are not necessarily equivalent to manually deleting an existing DOM attribute. `1008` captures normal/adaptive `originalBorderWidth`, distinct from the state width.

`style.js:750–751` is the image branch: when the border-width gate and pattern are truthy, it writes the pattern string directly into CSS `border-style`. It does not inspect `linePatternArray`. The probe demonstrates direct pass-through, not that every synthetic string corresponds to an actual native generated preset. In real CSS, `border-style:none` affects computed border width; the SVG paint rule does not itself change HTML layout. Do not apply a universal “none => layout widths zero” shortcut across both surfaces.

The implemented schema maps known native LineStyle1..9 to `solid`, `long-dash`, `medium-dash`, `short-dash`, `dash-dot`, `dash-dot-dot`, `long-dash-short-dash`, `dot`, `none`. Exact preset arrays and the bounded SVG cap findings are now recorded in [line-style-svg-evidence.md](line-style-svg-evidence.md). No arbitrary dash-array author field is implied by the runtime's permissive parser.

## 2. Visible sides and corners

`style.js:1228–1340` has a special branch only when `friendlyType === 'Rectangle'`. It rounds the widget's width/height with `Math.round`, derives four booleans from `borderVisibility`, and rebuilds stroke and fill independently.

- Logical side order is top, right, bottom, left. A new model can safely use an atomic four-boolean tuple in that order rather than conflating side visibility with stored per-side widths.
- Visible sides inset the centerline by half the current uniform border width; hidden sides leave that coordinate at the outer bound. E.g. a top-only border on 200×100 at width10 is `M 0 5 L 200 5`.
- Stroke corners require the corner's visibility and **both adjacent sides visible** (`1238–1241`). The radius ceiling changes depending on whether opposite corners require half-width/half-height, then is clamped to that ceiling. Its cubic approximation uses arc coefficient .44 (`1250–1256`).
- The builder begins after a missing edge, inserts fresh moves across disconnected edges, and appends `Z` **only when all four sides are visible** (`1308–1315`). All 16 side combinations are executed in the harness; radius0 emits exactly one line command per visible side and a closed path only for all four.
- Fill corner eligibility uses **equal adjacent side states**, not “both visible” (`1323–1326`). Thus top-only stroke removes its two top rounded corners from fill but retains the two bottom corners; all-hidden borders still retain a complete rounded fill. Fill then uses all four edges and closes regardless of stroke visibility.
- Both rebuilt paths clear their old mask attributes (`1317–1320`, `1337–1340`). Changing visibility replaces the path, removing previous corners rather than adding a CSS color overlay.
- `_updateCornersForBorders` (`935–961`) applies matching corner-suppression classes to the separate `_div` element using equal adjacent side states. The original cornerVisibility string uses unusual positions: top→top-right, right→bottom-right, bottom→bottom-left, left→top-left. Do not reinterpret it as conventional TL/TR/BR/BL without mapping.

This is positive evidence for the Rectangle runtime. It does not establish the same path-rewrite algorithm for every arbitrary vector, ellipse, image, form control, panel or native generator primitive. Original runtime uses a uniform border width here; the independent model's existing different per-side widths are an additional geometry requirement.

## 3. Line ends, caps, joins and paint interactions

For non-rectangle paths (`1341–1353`), closed-and-masked paths receive twice the requested stroke width, whereas open/unmasked paths receive the requested width. Dash lengths still use the requested width, even when the actual masked path stroke is doubled. In the unmasked branch the arrowhead CSS stroke width is `current border width - normal/adaptive original border width`; shrinking can produce a **negative value**, and no clamp exists in the source function. Browser treatment of that invalid negative CSS declaration depends on the initial generated arrowhead attributes and is not measured by these mocked probes.

`1182–1218` applies solid/linear/radial border paint to the stroke and arrowhead fill/stroke; the previous [gradient border investigation](gradient-border-runtime-evidence.md) records channel-specific definition reuse. Pattern, paint and shadow are independent style fields. The new harness confirms gradient paint, scaled dash sequence and outer shadow can coexist in one generated stylesheet.

- Outer shadow (`1390–1403`) targets the entire SVG, including painted paths and line ends.
- Inner shadow (`1491–1492`) targets `.fill` and `.background-image` only, not `.stroke` or `.arrowhead`. Its filter definitions coexist with gradient definitions.
- Line-friendly types set SVG overflow visible (`1373`).
- The JS painter does not change cap/join attributes or arrowhead path data. A bounded probe with an existing round cap, bevel join and arrowhead path leaves those attributes/geometry unchanged while changing width. This does not establish which attributes the original generator writes initially.
- Checkbox/radio have separate checks in `1375–1386`; generic line-end behavior must not be applied to native form glyphs just because they contain SVG paths.

The separate metadata and arithmetic investigation below establishes the 29 ArrowStyle members, Start/End pair, dimensions and placement quirks. The runtime does not justify inventing independently editable cap/join controls. Whole-generator compound-contour admission and native curve-offset pixels remain bounded unknowns.

## 6. Implemented contract and explicit limits

The portable factory is `src/model/line-style.ts`; gradients remain independently defined by `src/model/gradient.ts`. Author canvas, Preview, standalone HTML and the fixed internal-frame player receive the same helpers. The factory imports only TypeScript types; its serialized function has no module value or DOM dependencies. No vendor source was copied into product files.

- Nine patterns use the exact retained arrays multiplied by current width. The SVG exporter evidence does not forward the native pen's Round DashCap; the independent SVG uses butt/miter. There is no editable cap/join field. Image CSS groups preserve the proved grouping (long/medium/short/long-short together; dot/dash-dot/dash-dot-dot together). Assigning the words dashed/dotted to the unresolved native string keys remains a documented mapping inference, not decoded-literal evidence.
- Pattern, stroke paint, line ends and side visibility are independent. Atomic state/action/adaptive replacement comes from the shared model; an explicit solid stroke clears only inherited strokeGradient, not pattern or endpoints. Fill and stroke keep distinct gradient IDs and definition sessions. Outer shadow includes ends; inner shadow remains restricted to the fill.
- Line and each nonempty open vector contour receive endpoints. Closed contours do not. This independently supported compound-contour policy is not represented as proof of every original generator admission route. Move-only closed contours emit no isolated Z; a later empty contour cannot close an earlier open one.
- The old vector path is the baseline geometry. Merely recognizing a strict rectangle does not authorize replacement. Rebuilding occurs only for a box path with explicit partial-side visibility, using radii proven by that path rather than an unrelated style.radius default. Edited or reversed paths outside the exact clockwise rectangle family retain their explicit geometry. The native format agent independently verified all 31 admitted partial-side rectangle paths against this validator.
- Ordinary rectangular surfaces use original adjacent-side equality for fill corner suppression. Partial side paint is represented by an SVG background; HTML layout border widths remain intact. When side widths differ, each visible side is painted at its own width and clipped to its own region, eliminating hidden-neighbor spill. This per-side extension is verified against real browser pixels, not claimed as a recovered uniform-native-width formula.
- Image pattern uses CSS borders and the prior gradient image fallback; no image per-side editing. Inline Frame/hotspot exclude these paint controls. Generic form/container rectangular paint is an independently supported surface; the original runtime's Rectangle path branch alone does not prove every native generator type gate.
- SVG None paints shaft width0 and suppresses endpoints. Width0 draws no forced 1px line. These are intentional coherent independent rendering behaviors. The original state painter's truthiness gate, negative delta stylesheet and stale arrow stroke residue remain recorded in sections1/3; the product does not reproduce those stale-initial-path artifacts. Dynamic endpoints are regenerated from the current effective style.

## 8. Packaged visual QA correction: shared gradient coordinates at arrowheads

After initial source freeze, the parent inspected the packaged demonstration and found the shaft's blue-to-red gradient ending in a **blue** right arrow. This was a real product defect, not an original-program ambiguity. The independent renderer placed local endpoint geometry inside a translated/rotated SVG group, but reused a widget-space userSpaceOnUse gradient without cancelling that group's transform. As a result, the arrow sampled the beginning of the gradient in its local coordinates.

Evidence is now closed by [probe-line-style-arrow-paint.mjs](scripts/probe-line-style-arrow-paint.mjs) and [line-style-arrow-paint-probes.json](line-style-arrow-paint-probes.json). The bounded static CIL replay supplies nonzero positions and four directions to native `o5R8.i5RQ`100718992. All24 combinations (three polygon primitives, two widths, four placements) produce coordinates already transformed into the supplied widget space. Original `style.js:1182–1218` uses the same stroke gradient reference for the shaft and arrowhead fill/stroke. Together these support one continuous paint field over the positioned geometry. This does not claim an original GUI screenshot comparison.

The correction leaves endpoint geometry unchanged. Each painted endpoint gets a unique gradient definition with `gradientTransform = inverse(groupTransform) × originalGradientTransform`. For linear paint the second transform is identity; for radial paint the original rotated/scaled basis stays on the right. The browser then composes `group × inverse(group) × basis`, recovering the shaft's widget-space paint coordinates. Definitions are local to the endpoint group with instance-unique IDs; baseline stop/offset sessions remain immutable and independent across rows. Pure solid paint needs no extra definition.

Actual Edge regression first failed on the unpatched implementation: at the straight right triangle's interior pixel(190,40), expected red[255,0,0,255], observed blue[0,0,255,255]. The unchanged expected pixel passed after the correction, along with left endpoints, rotated cubic endpoints and repeated-row hover changes (first row green/yellow, second row still blue/red). Preview and actual offline export both passed (**2/2**,23.8s). The existing test now checks every gradient ID across both row instances is unique, including shaft and endpoint definitions. The new two unit cases check inverse-before-radial-basis multiplication and baseline immutability; final targeted unit total is **64/64** with typecheck passing.

The failed screenshot is retained as `artifacts/line-runtime-arrow-paint-before.png`. The four regular screenshots were replaced with post-fix captures; the new offline studio was visually inspected and its right gradient endpoints now visibly match their shaft end colors. The parent will rebuild and repeat full production/package verification against the corrected bytes.
